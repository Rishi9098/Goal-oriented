# 12 — Final Recommendation

**Date:** 2026-07-08
**Status:** Research conclusion. Direct answers to the seven questions asked, each traceable to the evidence documents.

---

### 1. Which model should Northstar start with?

**Qwen3-8B-Instruct (Q4, via llama.cpp/Ollama-MLX), with Qwen3.5-9B evaluated head-to-head in week one** and adopted if it wins on the product eval set. Basis (`01_Model_Comparison.md`): the only family simultaneously Apache-2.0 end-to-end, top-of-open-class at tool calling (BFCL evidence at family level), sized for the 16 GB M4 (~5–7 GB at Q4), strongly multilingual for the Hindi roadmap, and shipped with a first-party embedding line. **Phi-4-mini (MIT)** as the small/fast tier; **Qwen3-32B / GLM-4.5-class** as the future hosted tier. The instruction was not to default to Qwen — the comparison was run honestly, and Qwen won on structure (license + tool calling + hardware fit), not fashion.

### 2. Should we fine-tune immediately?

**No.** Fine-tuning is a V2 decision gated by evidence: it happens only if V1's evaluation shows prompt-resistant failures in tool formatting, refusal discipline, or voice (`04_Training_Strategy.md`). The literature is unambiguous that weights are the wrong home for time-varying financial facts (FinRAG/domain-survey evidence), and FinGPT-vs-BloombergGPT is the cost proof ($300 LoRA beats $3M pretrain). When the gate opens: **QLoRA on one L4-class GPU ($5–30/run), on synthetic data generated by Northstar's own engines** — never on real user data, never for knowledge injection.

### 3. Should we build RAG first?

**Build the tool layer first; RAG second — both in V1.** Reason: ~80% of real user questions ("will I hit my retirement goal?", "who's uninsured?", "which schemes apply to us?") are answered by **engines** (T0), not documents; the engines already exist, certified, with structured explanations attached. RAG (T2) adds the explanatory layer — *why 80D matters, how SSY works* — and is a smaller V1 scope: pgvector on the existing Postgres, BGE-M3, a curated effective-dated corpus of dozens (not thousands) of documents (`05_RAG_Architecture.md`).

### 4. Should we build tool calling first?

**Yes — it is the product.** The tool layer is a thin, typed façade over ten already-certified service functions (`06_Tool_Calling.md` §1 mapping table). It is simultaneously the highest-value and lowest-risk component: read-only by construction, auth-injected (cross-tenant injection unexpressible), covered underneath by 330 existing tests. One flagged gap: `calculate_tax` needs a deterministic tax engine that does not exist yet — that is future *engine* work; until then the assistant honestly declines tax computation.

### 5. What is the ideal architecture?

The convergent production pattern (`02`), enforced rather than requested (`00`):

```
User → guard/intent router → LLM (Qwen3-8B, local)
         ⇄ read-only tools → certified engines (T0) + versioned fact tables (T1)
         ⇄ hybrid RAG → effective-dated curated corpus (T2, pgvector + BGE-M3)
       → deterministic grounding validator (every number/citation must trace
         to this turn's tool outputs or chunks; fail ⇒ templated engine output)
       → reply with citations + tier provenance → audit trail
```

Serving: OpenAI-compatible local endpoint behind the existing `copilot.py` seam; `LLM_PROVIDER` switch keeps GPT-4o optional and the certified rule-based fallback as kill switch. Everything reuses what Northstar already operates: Postgres, pytest, structured logging, the audit pattern, Rule 10.

### 6. What mistakes should we avoid?

1. **Letting the model be an authority** — any design where a number can reach the user without passing through engine/table/validator (the root cause of every public financial-LLM failure).
2. **From-scratch or continual pretraining** — BloombergGPT's $3M lesson.
3. **Fine-tuning to inject knowledge** — facts go stale quarterly; weights can't be audited; Rule 2/4 violations by construction.
4. **An unversioned corpus** — RAG without effective-dating *will* cite last year's limit confidently.
5. **Shipping evaluation last** — the harness is the instrument every later decision (tuning? model upgrade? Hindi?) depends on; build it with V1, not after.
6. **Training on real user data** — permanent PII liability for marginal gain; synthetic-from-engines is better data anyway.
7. **Client-facing day one** — dogfood first (Morgan Stanley lesson).
8. **Framework maximalism** — the agent loop is ~200 lines; LangChain-class dependencies add attack surface and obscure the validator's seat.
9. **Skipping the SEBI/advice legal review** — the education-vs-advice boundary must be counsel-approved before default-on ( `08` §5).
10. **Buying hardware early** — the M4 is sufficient for all of V1; first GPU spend is a $30 QLoRA experiment, not a server.

### 7. What would I build if I were CTO of Northstar?

Exactly the V1 in `11_Roadmap.md`, sequenced so trust compounds: **eval harness + tool layer + grounding validator first** (the safety spine), model serving behind the existing provider seam second, minimal effective-dated RAG third, dogfooding-only exposure fourth — then let the evaluation numbers, not enthusiasm, dictate every escalation (fine-tuning, Hindi, default-on, writes). The strategic asset to protect is the one competitors cannot copy quickly: **certified deterministic engines with structured explanations, versioned policy truth, and now a narrator that is architecturally incapable of lying about them.** The local model is not a cost optimization — it is the privacy differentiator ("your financial life never leaves your infrastructure") that a GPT-4o-dependent competitor structurally cannot claim.
