# Risk Checklist — Milestone 2 (Family Financial Planning)

**Date:** 2026-07-06. Risks specific to this milestone's implementation, distinct from `RiskRegister.md`'s product-wide risks (referenced, not duplicated, where they overlap).

| # | Risk | Severity | Likelihood | Mitigation |
|---|---|---|---|---|
| 1 | The education-cost inflation "suggested rate" (§9) gets invented under implementation time pressure instead of verified or omitted. | High | Medium | Task 9 explicitly names this as its top risk; code review must reject any hardcoded rate not traceable to a verified source, per `docs/ENGINEERING_CONSTITUTION.md` Rule 4. Ship with no suggested default if verification isn't complete by Task 9's start. |
| 2 | The household-ownership authorization check (first "act on data that isn't directly your own `user_id`" pattern in this codebase) has a subtle gap, allowing cross-household access. | High | Low-Medium | Task 2 requires an explicit negative-path test (cross-household access attempt → `404`) for every single endpoint, not just the happy path — treat this as a security-review-triggering change per `rules/ecc/common/code-review.md`'s "authentication or authorization code" trigger. |
| 3 | The SSY 10-years age-boundary (inclusive vs. exclusive of the exact 10th birthday) is implemented inconsistently between the Add Child inline callout and the Schemes screen, since both consume the same service (Task 3) but could drift if the service's contract isn't pinned precisely. | Medium | Low | Task 3 is deliberately ordered *before* both consumers specifically to prevent this — a single shared, unit-tested function is the mitigation by construction, not an afterthought. |
| 4 | The mandatory joint-goal disclosure copy (`UX_REVIEW.md` revision #2) is watered down, made dismissible, or omitted during implementation, silently reintroducing the overpromising risk the review was written to catch. | High | Medium | Explicit acceptance criterion in `AcceptanceCriteria.md` ("renders every time, not a one-time tooltip"); flag for product/design sign-off specifically on this one piece of copy before Task 8 merges, not just a general QA pass. |
| 5 | The Family Dashboard (§12) silently recomputes retirement/emergency readiness instead of calling the existing `planning_service`, causing the two dashboards to drift out of sync over time as one is updated and the other isn't. | Medium | Medium | `AcceptanceCriteria.md` requires a byte-identical comparison test between `/family/dashboard` and `/dashboard`'s equivalent fields — this is a regression test that will fail loudly the moment drift is introduced, not a one-time check. |
| 6 | Mobile bottom-nav restructuring (Family added, Reports/Profile/Settings demoted to "More") regresses discoverability of those three routes without anyone noticing until a support complaint. | Medium | Medium | `UX_REVIEW.md`'s Product Designer finding already flags this as unresolved; Task 5 requires an explicit regression test that Reports/Profile/Settings remain reachable within 2 taps on mobile, and recommends instrumenting actual usage post-launch rather than assuming the restructuring is correct forever. |
| 7 | `has_own_insurance='not_sure'` gets treated identically to `'no'` somewhere in the recommendation logic, subtly misrepresenting an honestly-uncertain answer as a confirmed negative. | Low-Medium | Low | Task 10's implementation must branch on all three values explicitly (not `if has_own_insurance != 'yes'`), and a unit test should assert `'not_sure'` and `'no'` produce the same recommendation *outcome* by design (both should surface the recommendation) while remaining distinguishable in any copy that references the parent's stated certainty. |
| 8 | Scope creep: mid-implementation, a developer "fixes" Finding E (true joint-goal ownership) or builds HUF UI, since the underlying schema/entities already exist and it would be "easy while I'm in here." | Medium | Medium | This document and `Milestone2ImplementationContract.md` explicitly name both as out of scope with reasoning; `docs/ENGINEERING_CONSTITUTION.md` Rule 7 (no premature abstraction) and this project's own "one milestone at a time" precedent are the standing defense — flag any PR that touches `huf_entities`-adjacent UI or attempts to change `goals.user_id`'s ownership semantics as an immediate scope-boundary violation requiring explicit sign-off, not a normal review comment. |
| 9 | The new `goal_household_members` many-to-many table (the first of its kind in this codebase — every prior relationship has been one-to-many) has an under-tested cascade-delete interaction when both the goal and the household member are deleted in close succession. | Low | Low | Task 1 requires a specific integration test for this exact sequence (delete member → verify tag row gone; delete goal → verify tag row gone; both in either order), not just independent single-deletion tests. |
| 10 | The scheme-eligibility cross-product evaluation (§11) becomes a real N+1 or slow query path as household size or scheme catalog grows beyond what's been tested. | Low | Low | `TestPlan.md` §8 requires an explicit query-count assertion (not just wall-clock timing) in the integration test, so a future regression in query efficiency fails a test rather than only showing up as a slow endpoint in production. |
